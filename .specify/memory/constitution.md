# LNReader Plugins Constitution

## Core Principles

### I. Standard Plugin Contract

Every plugin MUST implement the four mandatory methods of `Plugin.PluginBase`:
`popularNovels(pageNo, options)`, `parseNovel(novelPath)`,
`parseChapter(chapterPath)`, and `searchNovels(searchTerm, pageNo)`.
Optional capabilities (filters, settings, custom headers/CSS/JS) MUST follow
the type definitions in `src/types/plugin.ts`. Rationale: the mobile app and
the web playground consume this contract uniformly; deviations break loading.

### II. Multisrc-First

Sites running on a known CMS platform (Madara, LightNovelWP, ReadWN,
Fictioneer, etc.) MUST be added as entries to the corresponding template in
`plugins/multisrc/{template}/`, not as standalone plugins. Standalone plugins
are only permitted when the site has unique structure that no template covers.
Rationale: duplication across hundreds of sites is unmaintainable; one template
fix propagates to every generated plugin.

### III. Blacklist Compliance (NON-NEGOTIABLE)

Sites listed in `BLACKLIST.json` MUST NOT be re-added in any form without
explicit approval from the repository owners. This includes new plugin files,
multisrc site entries, or renamed domains pointing to blacklisted content.
Rationale: removal requests from site owners are legally and ethically binding.

### IV. Playground Verification Before Submission

A plugin change MUST be verified through the web playground (`npm run dev`
→ http://localhost:3000) exercising all four contract methods against real
site data before being considered complete. Rationale: there is no automated
unit test suite; live verification is the project's quality gate.

### V. Build Pipeline Integrity

Generated artifacts MUST NOT be edited by hand. `plugins/index.ts` is
generated by `scripts/generate-plugin-index.js`; `*][site].ts` multisrc outputs
are generated by `generate-multisrc-plugins.js`; `.dist/plugins.min.json` comes
from the manifest script. Regeneration order MUST be respected:
clean:multisrc → generate multisrc → generate index → compile → manifest.
Rationale: manual edits are silently destroyed by the next build.

### VI. TypeScript Discipline

Production compilation uses `tsconfig.production.json` with `noCheck: true`;
type errors therefore do NOT fail builds. All changes MUST additionally pass
`npx tsc --project tsconfig.json` and `npm run lint` locally. Rationale:
relying on the production build alone lets type regressions reach users.

### VII. Simplicity and Scraping Etiquette

Plugins MUST scrape only what the contract needs, reuse shared helpers in
`src/libs/` (fetch, storage, filters), avoid heavy per-chapter work, and use
`dayjs` for dates and `cheerio`/`htmlparser2` for parsing rather than regex
HTML parsing where structured parsing suffices. Rationale: plugins run on user
devices; bandwidth and CPU costs are paid by end users.

## Additional Constraints

- Runtime: Node.js >= 22 required for tooling; compiled plugins target
  CommonJS/ES5 per `tsconfig.production.json`.
- Path aliases are fixed: `@/*` → `src/*`, `@plugins/*` → `plugins/*`,
  `@libs/*` → `src/libs/*`. New code MUST use these aliases.
- Web UI changes MUST use the existing stack (React 18, TailwindCSS v4,
  shadcn/ui, Zustand/Redux Toolkit) and semantic tokens over raw colors.
- Secrets MUST NOT be committed. Site credentials belong in plugin Settings,
  not source code.
- Icons referenced in plugin metadata are fetched by
  `scripts/download-plugin-icons.js`; icon URLs MUST be reachable at build
  time.

## Development Workflow

1. Branch from `master`; keep changes scoped to `plugins/**` or the specific
   surface touched.
2. For multisrc additions: edit the template's site list, then run
   `npm run clean:multisrc && npm run dev` (or `build:full`) to regenerate.
3. Validate site configuration with `npm run check:sites` when touching
   plugin/multisrc site definitions.
4. Run `npx tsc --project tsconfig.json` and `npm run lint:fix` plus
   `npm run format` before committing (Husky pre-commit enforces formatting).
5. Verify in the playground per Principle IV.
6. Pushes to `master`/`main` touching `plugins/**`, `public/**`, or publish
   scripts trigger CI publication to the `plugins` branch — treat master as
   releasable at all times.

## Governance

- This constitution supersedes ad-hoc practices documented elsewhere; conflicts
  resolve in favor of this document until formally amended.
- Amendments require: a written proposal in the PR description, updated
  version per semver (MAJOR = principle removal/redefinition, MINOR = new
  principle or material expansion, PATCH = clarifications), and reviewer
  approval from maintainers.
- All PRs and reviews MUST verify compliance with Principles I–VII; violations
  block merge regardless of other quality signals.
- Use `AGENTS.md` for day-to-day agent guidance; this document governs what
  may never be violated even if AGENTS.md drifts.
